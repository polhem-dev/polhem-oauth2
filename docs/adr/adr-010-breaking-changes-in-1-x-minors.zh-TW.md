# ADR-010：1.x 的 minor 版本可以含破壞性變更，嚴格的語意化版本從 2.0 開始

[English](adr-010-breaking-changes-in-1-x-minors.md) | **繁體中文**

## 狀態

已採納（2026-10-21）。取代 `CHANGELOG.md` 中「自 1.4.0 起，破壞性變更會提升主版號」這句話。Polhem 框架採用相同的政策，
見它的 [ADR-052](https://github.com/polhem-dev/polhem/blob/main/maintainers/adr/adr-052-breaking-changes-in-1-x-minors.md)。

## 背景

1.0.0 於 2026-09-14 發佈，`CHANGELOG.md` 宣告依循語意化版本。之後的三個 minor 版本中，有兩個含有破壞性變更：

| 版本 | 日期 | 破壞性變更 |
|------|------|-----------|
| 1.2.0 | 2026-09-25 | 中轉以 data protection 保護快取項目；拒絕未列出的 redirect URI 與過長的 code 有效期間；Facebook token 端點的錯誤改為 `OAuth2Exception` |
| 1.3.0 | 2026-09-26 | token type 不是 `Bearer` 時登入失敗；共用的 `HttpClient` 不再跟隨轉址 |

這些都是改寫變更紀錄時才辨識出來的，當時的變更紀錄因此承諾自 1.4.0 起，破壞性變更會提升主版號。1.4.0 自己又違反了
這個承諾：Google、Auth0、Okta 與 Microsoft Entra ID 現在會檢查登入取得的 ID token，ID token 發給其他 client、由其他
issuer 發出，或 subject 與使用者資訊不同時，原本會成功的登入改為失敗。

這些破壞全都是行為的改變，不是 API 的改變。`PublicAPI.Shipped.txt` 與公開 API analyzer 會抓到被移除或改變的成員，
卻沒有任何機制會發現一個呼叫開始拒絕它原本接受的回應。所以變更紀錄中「依循語意化版本」這句話，是一個背後沒有機制的保證。

這些破壞大多是讓函式庫拒絕規範或 provider 自己的規則所禁止的東西，例如看不懂的 token type，或發給其他 client 的 ID token。
把它們一一延到主版本，等於讓已知的弱點在整個 1.x 期間都留著，或為了一個沒有遷移步驟的變更用掉一個主版本。

目前破壞的代價很低：沒有已知的 polhem-dev 組織以外的使用者依賴這些套件。

## 決策

### 1. 1.x 的 minor 版本可以含破壞性變更

在 1.x 期間，**minor** 版本可以改變行為，讓原本成功的呼叫失敗或回傳不同的資料，也可以移除、改名或改變公開 API。
**patch** 版本不行：它只修正缺陷，不移除也不改變 `PublicAPI.Shipped.txt` 中的任何項目。

### 2. 每一項破壞性變更都要列出，不論理由為何

破壞性變更在 `CHANGELOG.md` 以一句話標示 **Breaking:**，並連到 `docs/en/changelogs/` 下該版的發佈說明；發佈說明寫出它影響誰、
之前與現在的行為，以及如何遷移。只要一個在前一版能運作的應用程式可能在這一版失敗，這個變更就是破壞性的，即使它只是落實
規範、沒有需要遷移的步驟。1.3.0 的 token type 檢查就是這樣列出的，1.4.0 的 ID token 檢查也照同樣的方式列出。

### 3. 使用者把版本固定在一個 minor 版本內

`CHANGELOG.md` 與 `README.md`（兩種語言）說明這項政策，並建議套件參照使用限制在一個 minor 版本內的範圍，例如 `[1.4,1.5)`，
而不是浮動的 `1.*`。

### 4. 從 2.0 起，以套件驗證執行語意化版本

2.0.0 開始採用嚴格的語意化版本，同一版對每個可封裝的專案開啟 .NET SDK 的套件驗證：`EnablePackageValidation`，並將
`PackageValidationBaselineVersion` 設為上一版，讓 `dotnet pack` 遇到 API 或二進位不相容時失敗。套件驗證看不到行為的改變，
所以從 2.0 起，這類變更要等到主版本，由它的審查來判斷。

### 5. 何時發佈 2.0

2.0.0 在下列條件中最先成立的那個時候發佈：

- 已知有 polhem-dev 組織以外的使用者依賴這些套件，或
- 連續兩個 minor 版本沒有任何 **Breaking:** 項目。

維護者可以更早發佈 2.0；這些條件是為了確保它不會被無限期延後。

## 影響

- **1.x 的版號不代表相容性。** 使用者從變更紀錄得知相容性，固定 minor 版本的建議才是保護他們的方式。
- **函式庫一發現該拒絕的東西，就能拒絕。** 像 ID token 這樣的檢查在下一個 minor 版本就能發佈，不必等到 2.0。
- **發佈說明就是機制。** 在 2.0 之前沒有工具能發現行為上的破壞，所以每個 pull request 的審查都要問：這項變更會不會讓一個
  能運作的應用程式失敗？會的話就要列出。
- **1.2.0 與 1.3.0 事後看來是一般的 1.x 版本。** 它們的破壞性變更照原樣列出。

## 考慮過的替代方案

### 每項破壞性變更都提升主版號

在語意化版本下完全正確，也是變更紀錄原本的承諾。不採用：1.4.0 會變成 2.0.0，而以 1.2.0 與 1.3.0 的步調，每隔幾天就會有
一個主版本。這給使用者的資訊並不比本政策多，還會用掉 2.0 這個代表 API 穩定的里程碑。

### 只落實規範的變更不算破壞性

維持語意化版本，但只拒絕規範所禁止之物的變更不列為破壞性。不採用：provider 是否違反規範，應用程式無法事先得知，所以對
使用者而言，這類變更和其他破壞性變更一樣。它也與 1.3.0 列出 token type 檢查的做法矛盾；而「只拒絕規範禁止的東西」這個說法，
必須對規範的每一條都正確才成立。

- `docs/adr/README.md` 與它的翻譯：把這份紀錄加入索引。
