# Polhem.OAuth2 1.2.0 — 發佈說明

[English](../../en/changelogs/1.2.0.md) | **繁體中文**

本檔是 [CHANGELOG.zh-TW.md](../../../CHANGELOG.zh-TW.md) 中 `[1.2.0]` 條目的詳細內容。

本版強化 Polhem.OAuth2.AspNetCore 的後端中轉，並讓 client 可以從 factory 取得 `HttpClient`。破壞性變更影響使用中轉的
應用程式，以及以 Facebook 登入、並依例外型別處理 token 請求失敗的應用程式。

## 新功能與變更

### 從 factory 取得 `HttpClient`

`OAuth2Client.Create(options, httpClientFactory)` 建立的 client 會為每一次對 provider 的請求索取 `HttpClient`。
`AddOAuth2ClientWithHttpClientFactory` 則在 ASP.NET Core 以服務提供者給的 `HttpClient` 註冊 client，例如來自
`IHttpClientFactory` 的，這樣它的 handler 輪替才會生效。

### 開始中轉登入

- `OAuth2Manager.TryRedirectToAppAuthorization` 以請求帶來的值開始一次中轉登入；client 名稱、回呼網址或 code challenge
  不合法時回傳 false，而不是擲例外。應用程式開啟的端點不必再靠 catch 例外來回應 400。
- `OAuth2Manager.CreateAppAuthorizationUrl`、`TryCreateAppAuthorizationUrl` 與 `CreateAppRedirectUrlAsync` 回傳中轉登入的
  網址而不是導向回應，與網頁登入的 `CreateAuthorizationUrl` 相同，給想自己導向的呼叫端使用，例如 minimal API。
  會導向的那幾個方法仍然保留。
- 回呼請求中斷時 `OAuth2Manager.RedirectToAppAsync` 也會停止，與 `CompleteAuthorizationAsync` 一致，因此不需要再傳入
  `HttpContext.RequestAborted`。

### `OAuth2Options.IsAppRedirectUri`

`OAuth2Options.IsAppRedirectUri` 檢查一個回呼網址能否把登入結果送回應用程式。這就是 `AppOAuth2Client` 原本套用的規則，
中轉對 `OAuth2AppRelayOptions.AppRedirectUris` 也套用它。

### 端點

- `AuthorizationEndpoint` 自帶的 query 會被保留，授權請求的參數接在它後面，符合 RFC 6749 第 3.1 節的要求。
  先前像 `https://tenant.auth0.com/authorize?audience=...` 這樣的端點會組出帶兩個問號的網址，被 provider 拒絕。
  Facebook 的 `UserInfoEndpoint` 同理。
- 端點帶有 fragment 時，建立 client 當下就會拒絕，符合 RFC 6749 第 3.1 節的要求。這種端點原本就無法運作，因為 fragment
  會吃掉接在後面的參數。

### 使用者名稱

回應裡沒有 name 時，每一家 OpenID Connect provider 的 `UserInfo.UserName` 都會退而把 given name 與 family name 接起來，
Microsoft Entra ID 原本就是這樣；Auth0 的 nickname 與 Okta 的 preferred user name 排在那之後。Facebook 也向 Graph API 多要
`first_name` 與 `last_name`，在 `name` 缺席時接起來，所以 Facebook 的 `UserInfo.RawJson` 現在多了這兩個欄位。

### 修正

- 兌換代碼的伺服器時鐘比發出代碼的伺服器快（一分鐘以內）時，中轉代碼不會再被提早拒絕。代碼的效期仍由快取在
  `CodeLifetime` 到期時結束。

## 破壞性變更

### 中轉保護快取裡的資料

- **影響對象：** 使用後端中轉、且 1.1.0 與 1.2.0 的伺服器共用同一個 `IDistributedCache` 的應用程式。
- **原本：** 1.1.0 在代碼兌換之前，把中轉登入的使用者資訊未加保護地存在快取裡，並且信任快取回傳的任何內容，因此快取
  必須跟應用程式本身一樣可信。
- **現在：** 中轉以 ASP.NET Core data protection、在它自己的 purpose 下保護快取裡的資料。兩個版本的伺服器共用同一個快取
  的期間，一個版本發出的代碼不會被另一個版本兌換。
- **遷移：**
  1. 共用中轉快取的伺服器一起升級。升級期間兌換失敗的代碼，重新登入即可。
  2. 每一台可能兌換代碼的伺服器都共用 data protection 金鑰環，與登入 cookie 原本的要求相同。
- **背景：** [ADR-006](../../adr/adr-006-app-sign-in.zh-TW.md)

### 中轉拒絕不在清單裡的回呼網址與過長的代碼效期

- **影響對象：** 使用後端中轉的應用程式。
- **原本：** 即使登入所指的應用程式回呼網址已從 `OAuth2AppRelayOptions.AppRedirectUris` 移除，`OAuth2Manager.RedirectToAppAsync`
  仍會導向它；`OAuth2AppRelayOptions.CodeLifetime` 沒有上限。
- **現在：** 該網址已不在 `AppRedirectUris` 裡時，`RedirectToAppAsync` 擲出 `InvalidOperationException`；`CodeLifetime`
  超過 10 分鐘時 `AddOAuth2AppRelay` 會拒絕，10 分鐘是 RFC 6749 第 4.1.2 節對授權碼的建議上限。
- **遷移：**
  1. 把 `CodeLifetime` 設為 10 分鐘以內。
  2. 以某個回呼網址開始的登入都結束之前，先把它留在 `AppRedirectUris`。進行中的登入最長 10 分鐘。
- **背景：** [ADR-006](../../adr/adr-006-app-sign-in.zh-TW.md)

### Facebook token 端點的錯誤改為 `OAuth2Exception`

- **影響對象：** 以 Facebook 登入、並依例外型別處理 token 請求失敗的應用程式。
- **原本：** Facebook 回傳的是 Graph API 的錯誤物件，被當成沒有錯誤代碼的回應，成為 `HttpRequestException`。
- **現在：** 與其他 provider 一樣成為 `OAuth2Exception`。`Error` 是 Graph API 錯誤的數字代碼，`ErrorDescription` 是它的訊息。
- **遷移：** 在 `AuthorizationResult.Exception` 與 `RefreshTokenAsync` 周圍，以 `OAuth2Exception` 取代 `HttpRequestException`
  處理這些錯誤。見 [Facebook](../providers/facebook.md#錯誤)。
- **背景：** [ADR-003](../../adr/adr-003-exception-semantics.zh-TW.md)
