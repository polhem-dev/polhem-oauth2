# Polhem.OAuth2 1.0.0 — Release Notes

**English** | [繁體中文](../../zh-TW/changelogs/1.0.0.md)

This file holds the details behind the `[1.0.0]` entry in [CHANGELOG.md](../../../CHANGELOG.md).

The first release under the Polhem name. It continues [Bee.OAuth2](https://github.com/jeff377/bee-oauth2), and
"breaking" below means breaking relative to the last Bee.OAuth2 release. The step-by-step guide is
[Migrating from Bee.OAuth2](../guides/migrating-from-bee-oauth2.md).

## New features and changes

### Desktop and console sign-in through the system browser

`LoopbackOAuth2Client` signs in from desktop and console applications through the system browser and a loopback
redirect, always with PKCE, on Windows, macOS and Linux. See [Desktop and console applications](../guides/desktop.md)
and [ADR-004](../../adr/adr-004-system-browser-loopback.md).

### The authorization code flow without an HTTP framework

`OAuth2Client` runs the authorization code flow in two steps, `CreateAuthorizationRequest` and
`CompleteAuthorizationAsync`, so a server framework other than the two web packages can use it. See
[Other server frameworks](../guides/other-server-frameworks.md).

### Tokens and refresh

`TokenResponse` holds the access, refresh and ID tokens with their type, lifetime and scopes.
`AuthorizationResult.Token` carries it, and `RefreshTokenAsync` on each client obtains new tokens. See
[Results, tokens and errors](../guides/results-and-errors.md).

### ASP.NET Core registration

`AddOAuth2Client` registers a client, `OAuth2Manager` and data protection in an ASP.NET Core application. See
[ASP.NET Core](../guides/aspnetcore.md).

### Errors from the provider

`OAuth2Exception` is thrown for protocol failures. Its `Error` and `ErrorDescription` carry the error code and description
returned by the provider.

### Providers

- `AzureOAuth2Options.Tenant`, for applications registered in a single Microsoft Entra ID tenant.
- The Okta provider, `OktaOAuth2Options`. An empty `AuthorizationServerId` selects the org authorization server.
- The LINE provider reads the email address from the ID token.
- Facebook uses Graph API v26.0, and Google uses its current authorization and user information endpoints.

### HTTP clients, cancellation and annotations

- Every client accepts an `HttpClient`, and asynchronous methods take a `CancellationToken`.
- Polhem.OAuth2 has a net10.0 target, which has no package dependencies.
- The public API has nullable reference type annotations.

### Security hardening

- Each sign-in has a new random state and PKCE code verifier, and web applications keep them encrypted and authenticated
  until the callback. The sign-in cookie uses the `__Host-` prefix and is Secure, HTTP-only and SameSite=Lax.
- The loopback listener ends the wait only for a request that names the redirect URI's host and carries the state of the
  sign-in, and it reads connections side by side.
- Provider endpoints must use https; see
  [Options are checked and PKCE is on by default](#options-are-checked-and-pkce-is-on-by-default).

## Breaking changes

### Packages, namespaces and target frameworks change

- **Affects:** every application that referenced Bee.OAuth2.
- **Before:** the packages were `Bee.OAuth2`, `Bee.OAuth2.AspNet` and `Bee.OAuth2.AspNetCore`, in the `Bee.OAuth2`
  namespaces. Bee.OAuth2.AspNet targeted .NET Framework 4.8, Bee.OAuth2.AspNetCore targeted net8.0 with the
  `Microsoft.AspNetCore.Http.Abstractions` package, and the packages depended on `Bee.Base` and `Newtonsoft.Json`.
- **Now:** the package IDs and namespaces start with `Polhem.OAuth2`. Polhem.OAuth2.AspNet targets .NET Framework 4.7.2,
  and Polhem.OAuth2.AspNetCore targets net10.0 and references the ASP.NET Core shared framework. JSON is parsed with
  System.Text.Json, which the netstandard2.0 build references as a package; the packages no longer depend on `Bee.Base`
  or `Newtonsoft.Json`.
- **Migrate:**
  1. Replace the package references and the `using` directives, as the table in
     [Migrating from Bee.OAuth2](../guides/migrating-from-bee-oauth2.md) lists.
  2. Move an ASP.NET Core application that uses Polhem.OAuth2.AspNetCore to net10.0.
  3. An application that used `Bee.Base` or `Newtonsoft.Json` through these packages references them itself.
- **Background:** [ADR-001](../../adr/adr-001-drop-bee-base.md)

### The desktop packages are replaced by `LoopbackOAuth2Client`

- **Affects:** desktop applications that used `Bee.OAuth2.WinForms` or `Bee.OAuth2.Desktop`.
- **Before:** the sign-in ran in an embedded WebView2 window.
- **Now:** both packages and the embedded window are removed. `LoopbackOAuth2Client` in Polhem.OAuth2 signs in through
  the system browser.
- **Migrate:**
  1. Call `LoopbackOAuth2Client.SignInAsync` in place of the desktop `OAuth2Client.Login()`, `OAuth2Manager.Login(clientName)`
     and the synchronous `Authorization()`. `Caption`, `Width`, `Height`,
     `AuthorizationForm`, and the desktop `OAuth2Client`, `OAuth2Manager` and `StateStorage` have no replacement.
  2. Register the redirect URI again as a loopback URI, as
     [Registering a loopback redirect URI](../guides/desktop.md#registering-a-loopback-redirect-uri) describes. A URI that
     only worked inside an embedded browser, such as `https://login.microsoftonline.com/common/oauth2/nativeclient`, no
     longer works.
- **Background:** [ADR-004](../../adr/adr-004-system-browser-loopback.md)

### Types that are no longer public

- **Affects:** code that used the provider classes or the state storage of Bee.OAuth2.
- **Before:** the provider classes, `IOAuth2Provider`, `BaseOAuth2Client`, `IStateStorage`, `PkceHelper`,
  `OAuth2StateCryptor`, and the `OAuth2Client` and `StateStorage` types of the web packages were public.
- **Now:** they are removed from the public API.
- **Migrate:** use an options type, such as `GoogleOAuth2Options`, with a client or a manager.

### Results and user information are read-only

- **Affects:** code that created, changed or derived from `AuthorizationResult` or `UserInfo`, and code that read
  `AuthorizationResult.AccessToken`.
- **Before:** both types could be changed, and the result carried the access token alone.
- **Now:** both are sealed and read-only, and `AuthorizationResult.Token` replaces `AccessToken`.
- **Migrate:** read `Token.AccessToken`, and refresh with `RefreshTokenAsync` on the client, which returns a
  `TokenResponse`.

### Web sign-ins are kept in a cookie

- **Affects:** web applications on Bee.OAuth2.AspNet or Bee.OAuth2.AspNetCore.
- **Before:** the pending sign-in was kept in session state, with the `OAUTH2_STATE_KEY` environment variable, and the
  managers provided `GetAuthorizationUrl` and `ValidateAuthorization`.
- **Now:** each sign-in is kept in a cookie of its own, protected with ASP.NET Core data protection or `MachineKey`.
  `OAuth2Manager` provides `CreateAuthorizationUrl`, `RedirectToAuthorization`, `CompleteAuthorizationAsync` and
  `GetClient`. The ASP.NET Core methods take the `HttpContext`, and the System.Web `RegisterClient` takes the options.
- **Migrate:**
  1. Register each client with `AddOAuth2Client` in ASP.NET Core, or with `OAuth2Manager.RegisterClient(name, options)`
     in System.Web. Remove the session state setup and `OAUTH2_STATE_KEY`, unless the application uses them otherwise.
  2. Call `CreateAuthorizationUrl` in place of `GetAuthorizationUrl`, and `CompleteAuthorizationAsync` in place of
     `ValidateAuthorization`.
  3. A sign-in started before the upgrade does not complete after it; the user signs in again.
- **Background:** [ADR-005](../../adr/adr-005-web-sign-in-cookie.md)

### Options are checked and PKCE is on by default

- **Affects:** every application, through the options it passes in.
- **Before:** `UsePkce` was `false` by default, and the options were not checked when a client was created.
- **Now:** a client copies and checks its options when it is created. Endpoints must be absolute https URIs, and `Domain`
  of Auth0 and Okta accepts only https. `UsePkce` is `true` by default. A web client sends the client secret whenever one
  is set, also with PKCE; a loopback client sends it only to Google.
- **Migrate:** fix the options that the checks reject. A change to the options after a client is created does not reach
  that client, so create a new client instead. See [Options shared by every provider](../guides/options.md).

### Unexpected exceptions are thrown

- **Affects:** code that read every failure from `AuthorizationResult.Exception`.
- **Before:** the result collected any exception of the sign-in.
- **Now:** `AuthorizationResult.Exception` holds only the failures an OAuth2 sign-in is expected to produce; other
  exceptions are thrown. An error response from the token endpoint becomes an `OAuth2Exception`. Exception messages
  include the HTTP status code but not the response body.
- **Migrate:** let unexpected exceptions reach the application's error handling, and read the provider's error code from
  `OAuth2Exception.Error`. See [Results, tokens and errors](../guides/results-and-errors.md).
- **Background:** [ADR-003](../../adr/adr-003-exception-semantics.md)

### User information values change

- **Affects:** applications that store `UserInfo` values, above all the Microsoft Entra ID user identifier.
- **Before:** a field whose value was JSON null was an empty string. The Microsoft Entra ID user identifier was read from
  `oid`, and from `sub` when `oid` was missing.
- **Now:** a JSON null field is `null`, so fallback fields take effect, such as `nickname` when Auth0 returns `name` as
  JSON null. The Microsoft Entra ID user identifier is read from `sub`, which the OpenID Connect user information endpoint
  returns.
- **Migrate:** treat `null` as a missing value. An application that stored Microsoft Entra ID identifiers read from `oid`
  matches its users again, for example by email address, because `sub` differs from `oid`. See
  [Identifying users](../guides/identifying-users.md).
