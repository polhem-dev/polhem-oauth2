# Polhem.OAuth2 1.4.0 — Release Notes

**English** | [繁體中文](../../zh-TW/changelogs/1.4.0.md)

This file holds the details behind the `[Unreleased]` entry in [CHANGELOG.md](../../../CHANGELOG.md), which becomes
1.4.0.

This version adds GitHub, Sign in with Apple and any other OpenID Connect provider, returns the user of an access token
that a front end sends to its back end, and checks the ID token of a sign-in with the dedicated OpenID Connect providers.

## New features and changes

### GitHub

`GitHubOAuth2Options` signs in with GitHub, through a GitHub App or an OAuth App. `UserId` is the numeric account ID. When
the user keeps the email address private, the address comes from `/user/emails`: the primary one, if it is verified. A
failure of that request leaves `Email` null instead of failing the sign-in. GitHub requires the client secret for every
code exchange, so it is sent from a public client too, and a mobile application signs in to GitHub through the back-end
relay. See [GitHub](../providers/github.md).

### The user of an access token from a front end

`OAuth2Client.GetUserInfoAsync(accessToken)` returns the user of an access token that a front end obtained and sent to the
back end. Before it asks for the user information, it checks with the provider that the token was issued to `ClientId` or
one of the new `OAuth2Options.AcceptedClientIds`, and the check cannot be skipped. A refused, expired or foreign token is a
failed result.

| Provider | Support |
|----------|---------|
| Google, LINE | Supported. |
| Facebook, GitHub | Supported. They need `ClientSecret`, and accept only tokens issued to `ClientId`. |
| Microsoft Entra ID, Auth0, Okta | `NotSupportedException`, whose message points to the ID token. |

See [Apps with a separate back end](../guides/separate-back-end.md) and
[ADR-007](../../adr/adr-007-access-token-from-front-end.md).

### Any other OpenID Connect provider

`OidcOAuth2Options` signs in with any other OpenID Connect provider, such as Keycloak or GitLab, with endpoints set by hand
or read by `OidcOAuth2Options.FromDiscoveryAsync(authority)`, whose document must name the authority as its issuer.

- `ProviderName` is required, because users are identified by it.
- `UserInfoEndpoint` may be empty, and the user then comes from the ID token of the sign-in.
- Every ID token it reads must be issued to the client, and by `Issuer` when that is set, and the user information must
  have the subject of the ID token.

See [Other OpenID Connect providers](../providers/openid-connect.md) and
[ADR-008](../../adr/adr-008-generic-openid-connect-provider.md).

### Sign in with Apple

`AppleOAuth2Options` signs in a web application with Apple.

- The library signs the client secret, an ES256 JSON Web Token, with `PrivateKey`, the `.p8` file of a Sign in with Apple
  key, and `KeyId` and `TeamId`, and replaces it before it expires. A secret signed in advance is accepted in
  `ClientSecret`.
- `UserId` and `Email` come from the ID token, and the name from the `user` parameter that Apple sends only with the first
  sign-in of a user.
- `LoopbackOAuth2Client` and `AppOAuth2Client` refuse these options, and a mobile application signs in through the
  back-end relay.

See [Sign in with Apple](../providers/apple.md) and [ADR-009](../../adr/adr-009-sign-in-with-apple.md).

### Form POST callbacks

Apple returns to the callback with a form POST from its own site when the `name` or `email` scope is requested.

- `OAuth2Client.UsesFormPostResponse` tells whether the provider returns that way.
- The `OAuth2Manager` of Polhem.OAuth2.AspNetCore and of Polhem.OAuth2.AspNet read a POST callback from its form, and keep
  the pending sign-in of such a client in a `SameSite=None` cookie, which a browser sends with that request. Every other
  client keeps `SameSite=Lax`. The callback of such a client must accept POST and be left out of antiforgery validation.
- `AuthorizationCallback.User` and a constructor that takes it carry the `user` parameter of Apple to
  `CompleteAuthorizationAsync` of a server framework other than the two web packages.

See [Web applications: how a sign-in is kept](../guides/web-sign-in-state.md),
[Other server frameworks](../guides/other-server-frameworks.md) and
[ADR-005](../../adr/adr-005-web-sign-in-cookie.md).

### Security hardening: the ID token of a sign-in is checked

Google, Auth0, Okta and Microsoft Entra ID check the ID token of the sign-in, as `OidcOAuth2Options` does: its audience
(`aud`) must be the client, and the user information must have its subject (`sub`). Google also checks that the issuer
(`iss`) is `https://accounts.google.com` or `accounts.google.com`, and Auth0 that it is the host of the authorization or
token endpoint with a trailing slash, such as `https://<Domain>/`. Okta and Microsoft Entra ID do not check the issuer,
which their settings do not fix.

A sign-in that used to succeed now fails with `OAuth2Exception` when:

- the ID token cannot be read;
- the ID token is issued to another client;
- for Google and Auth0, the ID token names another issuer;
- the user information names another subject than the ID token.

A token response without an ID token, for example when `openid` is not requested, is not checked.

These checks are the ones OpenID Connect Core 1.0 requires of a client, in sections 3.1.3.7 and 5.3.2, so they reject
only a response that breaks the specification or was altered on its way. There is nothing to migrate. On 2026-10-20 the
four providers signed in with real accounts with the check in place, and every sign-in succeeded; the details are under
[Test results in ADR-008](../../adr/adr-008-generic-openid-connect-provider.md#test-results).

### LINE reads the email address only from an ID token for its channel

LINE leaves the email address out when its ID token has an authorized party (`azp`) other than the channel ID, or has
audiences besides the channel ID and no authorized party. LINE issues neither, so a sign-in is not expected to change.
See [LINE](../providers/line.md).

### Requests to providers

- Every request to a provider names the library in its `User-Agent` header, as `Polhem.OAuth2/<version>`, after the
  products of the default `User-Agent` of an `HttpClient` that the application passes in. The GitHub API refuses a
  request without one.
- Token requests send `Accept: application/json`. RFC 6749 already has the token endpoint answer in JSON, and GitHub
  answers in form encoding without the header.
- A token response with status 200 that names an `error` fails with an `OAuth2Exception` that carries the provider's
  error code, instead of the generic error about a missing access token. GitHub reports failures of its token endpoint
  this way.

## Breaking changes

None.
