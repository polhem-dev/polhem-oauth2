# Polhem.OAuth2 1.2.0 — Release Notes

**English** | [繁體中文](../../zh-TW/changelogs/1.2.0.md)

This file holds the details behind the `[1.2.0]` entry in [CHANGELOG.md](../../../CHANGELOG.md).

This version hardens the back-end relay of Polhem.OAuth2.AspNetCore and lets clients take their `HttpClient` from a
factory. The breaking changes affect applications that use the relay, and applications that sign in with Facebook and
catch the exceptions of a failed token request.

## New features and changes

### `HttpClient` from a factory

`OAuth2Client.Create(options, httpClientFactory)` creates a client that asks for the `HttpClient` of each request to the
provider. `AddOAuth2ClientWithHttpClientFactory` registers one in ASP.NET Core with an `HttpClient` from the service
provider, such as one from `IHttpClientFactory`, whose handler rotation is honored that way.

### Starting a relayed sign-in

- `OAuth2Manager.TryRedirectToAppAuthorization` starts a relayed sign-in with values that come from the request, and
  returns false for a client name, a redirect URI or a code challenge that is not valid, instead of throwing. An endpoint
  that an application opens no longer has to catch exceptions to answer with status 400.
- `OAuth2Manager.CreateAppAuthorizationUrl`, `TryCreateAppAuthorizationUrl` and `CreateAppRedirectUrlAsync` return the URL
  of a relayed sign-in instead of redirecting the response, as `CreateAuthorizationUrl` does for a web sign-in, for a
  caller that redirects in its own way, such as a minimal API. The methods that redirect remain.
- `OAuth2Manager.RedirectToAppAsync` stops when the callback request is aborted, as `CompleteAuthorizationAsync` does, so
  passing `HttpContext.RequestAborted` is no longer needed.

### `OAuth2Options.IsAppRedirectUri`

`OAuth2Options.IsAppRedirectUri` checks whether a redirect URI can return a sign-in to an application. It is the rule that
`AppOAuth2Client` already applied, and the relay applies it to `OAuth2AppRelayOptions.AppRedirectUris`.

### Endpoints

- The query of `AuthorizationEndpoint` is kept, and the parameters of the authorization request are added after it, as
  RFC 6749, section 3.1, requires. An endpoint such as `https://tenant.auth0.com/authorize?audience=...` produced a URL
  with two question marks, which the provider refused. The same applies to the `UserInfoEndpoint` of Facebook.
- An endpoint with a fragment is rejected when the client is created, as RFC 6749, section 3.1, requires. Such an endpoint
  never worked, because the fragment swallowed the parameters added after it.

### User names

`UserInfo.UserName` falls back to the given and family names joined for every OpenID Connect provider when the response
has no name, as it already did for Microsoft Entra ID; Auth0 falls back to the nickname and Okta to the preferred user
name only after that. Facebook asks the Graph API for `first_name` and `last_name` as well, and joins them when `name` is
missing, so `UserInfo.RawJson` from Facebook now includes those fields.

### Fixes

- A relay code is no longer refused early on a server whose clock runs up to a minute ahead of the server that issued it.
  The cache still ends the lifetime of the code at `CodeLifetime`.

## Breaking changes

### The relay protects its cache entries

- **Affects:** applications that use the back-end relay, while servers of 1.1.0 and 1.2.0 share an `IDistributedCache`.
- **Before:** version 1.1.0 stored the user information of a relayed sign-in unprotected in the cache until the code was
  redeemed, and trusted whatever the cache returned, so the cache had to be as trusted as the application.
- **Now:** the relay protects its entries with ASP.NET Core data protection, under a purpose of its own. While servers of
  both versions share a cache, a code issued by one version is not redeemed by the other.
- **Migrate:**
  1. Upgrade every server that shares the relay cache together. If a code fails during the upgrade, the user signs in
     again.
  2. Every server that can redeem a code shares the data protection key ring, as the sign-in cookie already requires.
- **Background:** [ADR-006](../../adr/adr-006-app-sign-in.md)

### The relay refuses an unlisted redirect URI and a long code lifetime

- **Affects:** applications that use the back-end relay.
- **Before:** `OAuth2Manager.RedirectToAppAsync` redirected to the application redirect URI that the sign-in named, even
  when it had been removed from `OAuth2AppRelayOptions.AppRedirectUris`, and `OAuth2AppRelayOptions.CodeLifetime` had no
  upper limit.
- **Now:** `RedirectToAppAsync` throws `InvalidOperationException` when the URI is no longer in `AppRedirectUris`, and
  `AddOAuth2AppRelay` rejects a `CodeLifetime` longer than 10 minutes, which RFC 6749, section 4.1.2, recommends for an
  authorization code.
- **Migrate:**
  1. Set `CodeLifetime` to 10 minutes or less.
  2. Keep a redirect URI in `AppRedirectUris` until no sign-in started with it is still in progress. A pending sign-in
     lasts about 10 minutes.
- **Background:** [ADR-006](../../adr/adr-006-app-sign-in.md)

### A Facebook token endpoint error becomes an `OAuth2Exception`

- **Affects:** applications that sign in with Facebook and handle a failed token request by its exception type.
- **Before:** Facebook reports a Graph API error object, which was read as a response without an error code and became an
  `HttpRequestException`.
- **Now:** it becomes an `OAuth2Exception`, as for every other provider. `Error` holds the numeric code of the Graph API
  error, and `ErrorDescription` its message.
- **Migrate:** handle `OAuth2Exception` in place of `HttpRequestException` for these errors, in
  `AuthorizationResult.Exception` and around `RefreshTokenAsync`. See [Facebook](../providers/facebook.md#errors).
- **Background:** [ADR-003](../../adr/adr-003-exception-semantics.md)
